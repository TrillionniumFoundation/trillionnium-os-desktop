# V2 ancillary receive ownership revision 2

This new revision fixes the independently reproduced SCM_PIDFD rejection leak in both the root factory request receiver and the client reply receiver. The original V2 component, candidate04, its successful preparation, and original failing controls remain unchanged. This revision has not started a factory service or run on Android.

Only SOL_SOCKET/SCM_PIDFD (Linux UAPI value 0x04) with a complete single int payload is treated as a pidfd. The existing FD owner closes that one descriptor, then the protocol still rejects the unexpected header with EPROTO. Credentials and other non-FD ancillary payloads are not interpreted as descriptor arrays. Existing SCM_RIGHTS ownership, truncation rejection and errno behavior remain in place. Older libc headers do not need to define SCM_PIDFD; headers that do define it are checked with static_assert.

CreateSnapshot's inline receive/parse stage was moved into a private ReceiveSnapshotReply helper in the same source file. Its root-peer authorization remains before that call; its full snapshot provenance and flags checks remain after it. No namespace, UID, root-peer or snapshot-authentication check was removed or bypassed. The actual helper is exercised directly by the new kernel socket controls; this does not claim full CreateSnapshot authentication/provenance or a trusted factory positive.

The local kernel 6.18.57 controls use real socketpair, sendmsg, recvmsg, poll, SCM_RIGHTS, SO_PASSPIDFD and SO_PASSCRED without syscall seams. Thirty-four controls pass, including ordinary frames, extra pidfds/credentials, partial and oversized frames, truncated ancillary, wrong rights count, error replies, and 32 repeated rejections at each endpoint. Every fixed receive leaves the complete preexisting FD set intact and introduces no leaked FD. The same gate fails against the original factory and an explicitly documented extraction of the original client receive stage: 13 failing rows expose the old leak. The controls precisely close only their newly received leaked objects to leave the test process clean.

The separate listener inheritance control is derived from root's actual Pocket4 kernel7.0.0-38 baseline source (1ab026f3...), with only the source include and expected cleanup result adjusted. It compiles locally but has not executed here; Pocket4 must rerun it against the new source. Root's old real listener baseline already proved that SO_PASSPIDFD=1 is inherited and produces the leak in candidate04. No local socketpair result is substituted for that device gate.

Source integration is exactly two candidate04 file replacements: host-factory-v2/source/factory_main.cc and engine/kernel_api/proc_maps_provenance.cc. All protocol/wire/context/header files, raw owner and six signal files are unchanged. Candidate05 needs a fresh complete manifest, strict matching Android translation-unit gates, actual listener control, and its own full engine build/source receipt. Main deployment, enabled lifecycle, trusted Android factory, NOFILE=0, host-native transitions, and all application acceptance remain unqualified.
