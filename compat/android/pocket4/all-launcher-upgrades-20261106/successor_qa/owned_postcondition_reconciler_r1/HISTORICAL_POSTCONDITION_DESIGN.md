## Proposed explicit historical producer

A separate producer would use operation `owned-qa-historical-postcondition-proof` and typed schema `pocket4-beike-owned-qa-historical-postcondition-proof-v1`, with a new source/request identity, new O_EXCL stage and new step. The current-context r2 publisher must not be patched or retried. Its failed step and bytes stay frozen.

The new producer would preserve the same full evidence validation and current identity checks:

1. Pin the actual private two-step bundle and original execution metadata. Reuse the unchanged pure r2 verifier (`28,714` bytes, SHA-256 `6f780bdd021942617a6817dbc449eeacc60eeda9972d619fdb192ec4ae313e41`) and the frozen real helper parser. Recompute every original request, exact argv/environment/authority FD layout, transport lease result, command stdout/stderr hash, assessment, helper nonce, idle/restoration result and source/build identity. Accept only the completed successful action and later completed independent inspect; errors, timeout, missing raw evidence, unknown observer or altered source fail closed.
2. Preserve both UTC and Android monotonic order, distinct nonces and distinct durable process/idempotency identities. Match only the explicitly selected unique visible nonpassword, untruncated home node from the later inspect. Do not assert absence of other nodes or infer current UI state.
3. Use the original Flow and action locks in a new nonmutating step, the original held R5 transport and current typed guard. Revalidate current epoch, process start identities, namespace type/device/inode, classpaths, Beike UID/APK/data, exact launch ownership/task 876 and installed helper UID/APK twice. The existing eight-site nsfs observation-mtime comparison stays narrowly scoped; every other identity/metadata field remains exact.
4. The existing current foreground diagnostic may be included as an actual, time-stamped observation, explicitly separate from the historical proof. It is not an admission condition or a current-page claim. The new producer need not execute another foreground query: its purpose is historical reconciliation, and original `Flow.reconcile` requires fresh exact task/guard rather than current focus. It must not call or replace `Session.foreground` under a more permissive predicate.
5. Re-read all original evidence and source/request pins, close only known owned authority/directory descriptors, require exact FD identity closure, preserve original lock lifetime and the proven library resource lifecycle. Only after these gates may it atomically publish one new, no-replace compatibility envelope. Any uncertainty at publication remains UNKNOWN; no automatic retry or replacement is allowed. Acceptance requires final original stdout and authoritative durable successful process termination, not an early proof file.

The proof must state the actual observed interval and both separate conclusions:

```json
{
  "semantic_scope": "historical_postcondition_only",
  "original_action_outcome": "unknown_retained",
  "postcondition_verified_at_observation": true,
  "postcondition_verified_now": false,
  "current_foreground_authorization": false,
  "current_task_identity_revalidated": true,
  "allows_new_decisions_only": true,
  "requires_unchanged_fresh_foreground_and_state_for_next_UI": true,
  "old_Flow_reconcile_called": false,
  "original_action_result_rewritten": false,
  "old_action_replayed": false,
  "business_success_verified": false,
  "production_ready": false
}
```

These are proposed field names, not a fabricated receipt. The compatibility envelope would retain schema `pocket4-flow-explicit-reconciliation-v1` solely because that is the existing consumer interface. It would hash the new typed historical proof and source/request plus all original action/observer evidence. The raw old action remains UNKNOWN. The record acknowledges the witnessed result at the observation time and permits a new guarded decision; it does not authorize a click, input or foreground transfer.

A separately proven existing-task activation path, or a later actual return of Beike to the foreground, is still required before business UI work can continue. The prepared search plan remains blocked and unrun.
