# Conditional design for an explicit owned-QA-case postcondition producer

Status: design only. No producer source, compatibility envelope, reconciliation
file or Main request is created by this document. The actual two-step case and
search-page evidence must settle before any executable binding is sealed.
The original Flow, its consumer, helper, Session foreground checks and existing
UNKNOWN results stay unchanged.

## Feasibility and scope

A legitimate separate producer is possible because the frozen recorder already
has a hash-bound reconciliation consumer. Its existing `Flow.reconcile` producer
accepts only the old `operation=ui` CLI protocol. The new producer therefore must
declare `owned-qa-case` as its real source protocol and use a new typed proof
schema. It cannot rename the case or any helper response into the old protocol.

The initial candidate should be narrow: the current Beike flow ending in
`b6de2bd4f04bcd572a074ef984ba7dbe`, task 878, Beike UID 10143, helper UID 10157,
the existing exact source/build/APK/signer pins, the actual framework/runtime/App
scope, this exact declared case, and one later independent inspection. These
are inputs to be sealed from actual receipts, not caller-selectable defaults.

The most conservative eligible case is a genuinely complete durable exit-0
case whose two action sequences and two independent post-inspections passed.
Its top-level UNKNOWN still remains. Any error, timeout, unjoined child, missing
receipt or failed assertion is retained and not automatically admitted by this
initial producer. A partial/failed case would require an explicitly reviewed
different evidence policy based on its actual outcome; it cannot inherit this
candidate's success assumptions.

## Evidence to collect after the real case

The exact original case plan, step intent/result, held binding, owned task scope,
all original command intent/result/stdout/stderr and all transport intent/result/
verified-result files must be pinned. Every nonce request and saved assessment
must be reparsed from its actual instrumentation raw using the unchanged
`qa_contract.py`. The two original `case-NN-operation.json` and two
`case-NN-postcondition.json` records must match the corresponding original raw.
No record can be generated from the plan and then passed off as an observation.

For this planned two-action case, the original source implies 38 recorded
commands, 50 held transport receipts and 14 helper nonces, plus the case files.
Those counts are an expected finite read set, not a statement that those files
already exist. Actual receipts must confirm the exact set; extras, gaps or
different ordering require review. Private foreground raw was intentionally
discarded by the original backend. The proof must not invent that raw or claim
to reparse it: it can bind the actual private transport hashes and successful
source-qualified sequence, and use the recorded helper scope/window evidence.

Each command must have the exact original argv/environment, source, held parent
PID and seven authority FDs, no retry, complete captured streams, normal joined
completion and matching lease/post-guard evidence. Descriptor numbers may differ
between separate owned processes; they must match each actual process's own
recorded authority, not be made equal across unrelated jobs. Library bootstrap
and owned-parent normal pidfd retirement must be the actual qualified protocol.

The strict wire parser must re-establish helper identity, nonce/request hash,
operation, complete selected window/tree/node hashes and restoration. The
original per-step postconditions must be recomputed with the original
`run_case.match_postcondition`, preserving all string truncation flags. This
does not turn the exploratory final `搜索` assertion into evidence of an editor,
results, business success or App readiness.

## A genuinely later final observation

Use the unchanged read-only helper entry for one new inspection after the case
has actually ended. `Flow.begin` permits read-only observations while UNKNOWN
remains. That observation must have its own complete durable exit-0 receipt,
new nonces, normal owned-child exit, unchanged task/helper/runtime/App identity,
before/after state restoration and current foreground checks.

The selected final postcondition comes from that actual new page. If it is an
input-ready proof, it must name the actual unique visible, non-password,
untruncated Beike EditText resource and class, with enabled/editable/set-text
capability. Do not infer those properties from a `搜索` label or metadata.
The observer's full original raw must recompute that node. Timestamp ordering
must place the case end before the independent observer start; genuine Android
elapsed times must also be ordered within the same qualified runtime. Host UTC
and elapsed-time evidence retain their actual units and integer precision.

During proof verification, acquire fresh original held R5 authority and recheck
the current exact leaf task, helper UID and full signed APK bytes, scope/source
closure, App/data identity and unchanged Session foreground predicate. Require
the observer and current foreground context to agree under that existing
contract. Only the eight demonstrated namespace-FD mtime observations may be
projected as in the proven original R5 comparison; namespace identity, process
start, APK/data/classpath files and every other metadata field remain exact.

## Publication is a new decision record, not an old result edit

The producer's typed proof must identify the true owned-case protocol and every
actual source, case, observer, runtime and lifecycle evidence hash. It records
that the postcondition held at the independent observation, not that the old
action has a newly known outcome. It cannot claim current UI text remains
unchanged after observation; the next original action still performs a fresh
inspection and foreground/task/helper checks.

Keep a verified proof candidate non-authorizing until its actual owned-process
retirement and complete durable controller outcome have been accepted. A small
separate final host commit can then validate those original receipts and publish
the typed proof and compatible consumer envelope exclusively. This avoids
publishing an authorizing envelope before an unknown late retirement outcome.
The concrete verifier/commit sequence and its exact source must receive a review
after real evidence exists; this document does not supply an executable shortcut.

The compatibility envelope retains the consumer's required schema,
unknown-step name, exact epoch and scope hash, complete relative evidence-hash
map, `original_action_outcome=unknown_retained` and
`allows_new_decisions_only=true`. Additional typed fields explicitly name the
new producer and real owned-case protocol. The original case, assertions,
failures, UNKNOWN flags and observer files are never modified. No existing
reconciliation may be overwritten or made applicable to another task or flow.

The final guarded step remains the unchanged consumer plus the unchanged fresh
UI admission. A new key, new step or second live flow cannot replace this proof.
If the evidence cannot meet the contract, retain UNKNOWN and use the separately
authorized original exact-owned-task recovery path; do not manufacture a proof
to keep the test moving. Bili, Meituan permission and integrity boundaries are
unchanged, and all production/readiness counts remain zero.
