# A09 cross-kernel GPU provenance gate

`acceptance.py` accepts four separate inputs:

```sh
python3 support/vmm/acceptance.py \
  --host host-vmm.json --host-log host-boot.serial \
  --guest linux-guest-gpu.json --guest-log guest-boot.serial --output acceptance.json
```

`host-vmm.json` **must be generated by trusted code in the actual
Asterinas-derived host** after an isolated lab VM, PCI assignment, interrupts,
DMA mappings, lifecycle and quiescence have been exercised. `guest` must come
from the Linux guest running the `run_isolated_cuda.py` CUDA GEMM. Both files
must retain real raw boot logs (with hashes and markers), same VM ID and fresh
boot nonce, host/guest PCI vendor/device IDs, matched guest PCI BDF, exact
GEMM result digest, and independent kernel/driver/firmware identities.

The sole acceptable status of a *consistent but unauthenticated* evidence
bundle is `independent_hardware_review_required` (exit 3). Failed or missing
gates return `blocked` (exit 2). **There is deliberately no success/zero exit
and no automatic `asterinas_gpu_verified=true`**, because unsigned JSON and
boot-log files are not cryptographic evidence of which kernel owns a physical
GPU. An attacker could forge both files. Only A00's independent hardware log
capture, reproducible binary hashes, device assignment/IOMMU trace inspection,
and fault/recovery review could ultimately qualify physical acceptance.

Proposed host JSON structure (fields are NOT currently emitted by any A01/A05
kernel implementation):

```json
{
  "schema": "a09.asterinas-host-vmm-evidence.v1",
  "host_kernel": "asterinas-derived",
  "upstream_pin": "c4b7ed575b7b32773475b194d2ad41fb6d03765b",
  "host_boot_log_sha256": "<actual 64-character lower-case sha256>",
  "host_boot_marker": "<marker present in actual serial log>",
  "vm": {
    "backend": "intel-vmx",
    "host_cpu_vendor": "GenuineIntel",
    "hardware_virtualization_executed": true,
    "guest_linux_booted": true,
    "vm_id": "<same actual VM identifier in guest>",
    "boot_nonce": "<same actual 128-bit random nonce in guest, hex>"
  },
  "device": {
    "owner": "asterinas-host-vmm",
    "host_bdf": "<actual physical BDF>",
    "vendor_id": "0x10de",
    "device_id": "<observed real PCI ID>",
    "iommu_group_complete": true,
    "iommu_dma_translation_enabled": true,
    "interrupt_remapping_enabled": true,
    "host_driver_detached_from_prod": false,
    "device_idle_isolated_lab": true,
    "DMA_quiescence_on_teardown_verified": true,
    "no_device_reset_during_test": true
  }
}
```

Example uses VMX on Intel; if host is actually AMD, `amd-svm` must have been
implemented and validated independently; **pinned upstream v0.19.0 VMX/EPT
files DO NOT establish SVM**. Guest manifest must contain actual Linux boot
log digest/marker, VM ID/nonce, guest PCI IDs/BDF, NVIDIA driver and GSP
firmware manifest digests (as applicable) and the literal JSON from bounded
CUDA GEMM. This is an **interface proposal**, not an implemented guest-host
attestation mechanism.

The tool never opens device nodes, binds PCI, resets cards or touches H3,
training or other production workloads. No remote inference counts as local.

## In-place evidence mutation race

The acceptance reader now compares the opened file descriptor's device/inode,
size, nanosecond modification time and metadata change time before and after
a bounded read. **Equal-length rewrites** or timestamp changes while reading
are rejected rather than accepted as a consistent capture. This is only
concurrent-modification detection: an attacker who controls the content and
associated JSON digests before the read can still manufacture a consistent
bundle. As before, even consistent unsigned evidence can only reach
`independent_hardware_review_required`, never an automatic GPU success.

CPU-only regression fixtures deliberately modify a same-size serial log and
a JSON manifest during a patched read. These paths do not access any GPU,
KVM, PCI devices or privileged kernel interfaces.

## Strict JSON evidence semantics

Host/guest JSON manifests and the CUDA subprocess's self-reported JSON now
reject **duplicate keys at any nesting depth** and non-finite `NaN` /
`Infinity` constants. Different JSON consumers must not interpret an
ambiguous record as different GPU device identities or status values.
Rejected records remain blocked/failed, not recovered. This is deterministic
parsing hardening only; unsigned evidence still cannot attest Asterinas
execution or physical CUDA computation.
