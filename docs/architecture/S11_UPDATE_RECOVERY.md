# S11 transactional A/B update and recovery

## Scope and claim ceiling

Source entry point: `platform/update_recovery.py`; executable host corpus:
`tests/test_s11_update_recovery.py`.

S11 implements a source and host mechanism candidate for signed A/B updates. It authenticates a closed manifest, verifies a complete target image before any staging write, publishes bytes only to a private regular-file inactive slot, requires exact boot identity and a health receipt before policy commit, and rejects ambiguous transitions.

The ceiling remains source behavior and host filesystem mechanics. No installed QEMU update, bootloader integration, block-device write, raw power loss, physical device, production signing-key custody, protected monotonic storage, publication or release readiness is proven. Update admission defaults to disabled without externally approved roots; every image staging receipt reports `production_activation_enabled=false`.

## Threat and authority boundary

Update metadata, detached signatures, candidate images and recovery assertions are untrusted. A manifest or checksum alone provides no installation authority. Trust-root configuration, the current running image identity, the protected rollback floor, the clock and approved local recovery accounts must come from the trusted installed adapter outside the update payload and repository checkout.

The coordinator retains the actual immutable ticket for one transaction. A copied ticket, stale sequence, wrong phase or unrelated permit is refused. Health permits and reconciliation facts must be the actual objects issued and retained by that coordinator; an equal manifest/sequence from a second coordinator does not grant authority. Python objects and callbacks are trusted in-process configuration, not an authentication boundary against arbitrary code already executing in the coordinator process. No network download, signing, key generation or release publication API exists. The one subprocess boundary is bounded offline `/usr/bin/openssl dgst -sha256 -verify`: a trusted root-owned system executable, no shell, no caller-supplied command, no input stream, no output disclosure and a 15-second timeout.

Verification uses three real Linux sealed memfds containing the exact retained public key, canonical preimage and detached signature. Each has write, grow, shrink and seal seals before launching OpenSSL; only these descriptors are inherited through `pass_fds` and addressed by `/proc/self/fd/<fd>`. There are no mutable verifier input pathnames. Every descriptor closes on success, rejection or interruption. Missing memfd/seal support fails admission. OpenSSL receives only `PATH=/usr/bin:/bin`, `OPENSSL_CONF=/dev/null` and `LC_ALL=C`; caller configuration, provider and loader environment variables are not inherited.

Every coordinator, verifier and private store belongs to its creating process and creating thread. Authority entrypoints check this ownership before using snapshots, tickets, permits, directories, leases or journal facts. A fork child cannot verify, stage, write, commit or reconcile through inherited objects, even if its copied health permit predates a parent failure. A different thread cannot use or close those objects. Construct the objects on the actual owner thread and serialize queued work there; the API does not transfer ownership. Callbacks are trusted, nonreentrant configuration and must not fork or reenter an ongoing update operation. These rules do not sandbox arbitrary Python code or make caller-supplied health assertions into installed observations.

Configured roots, signature verifiers, journal authorities and image slot stores must have the exact concrete types `UpdateTrustRoot`, `ExternalUpdateSignatureVerifier`, `DurableUpdateJournal` and `ImageSlotStore`. Subclasses and duck callbacks cannot substitute verification, manufacture durable journal facts or return a fabricated staging receipt. The separately documented clock and fault hooks remain trusted host configuration. Exact types are an API admission rule, not protection from arbitrary Python code mutating the module or an accepted instance.

One exclusive nonblocking filesystem lease protects each private store. Every operation revalidates the root pathname, retained directory inode, private ownership/mode and named lease inode. A replaced lease or authority directory is refused; existing unsafe permissions are not silently repaired. `close()` closes descriptor copies without calling `LOCK_UN`; Linux releases the shared open-file-description lease only when its last descriptor copy closes. A fork child may only perform this cleanup, so its close cannot unlock a live parent coordinator. A child retaining a copy can delay lease release and must exit or close it before a replacement coordinator acquires authority. This supports cooperating coordinators under the private-directory custody assumption. Filesystem write access by a malicious coordinator account remains a compromise; a local unkeyed file is not an independently protected monotonic anchor.

Callers should explicitly close stores. Discarded stores also have descriptor-only garbage-collection cleanup, which may run in another thread or a fork child. It closes retained copies without checking authority ownership, writing a receipt, committing, reconciling or explicitly unlocking. Constructor descriptor fields start empty, and cleanup clears them before closing; a failed constructor cannot later close a descriptor number reused by another file. Garbage collection supplies no transaction result or durable recovery decision.

## Manifest admission

The v1 manifest is one strict UTF-8 JSON object with the exact contract field set. Duplicate members, BOM, nonfinite numbers, unknown fields, malformed identifiers and over-limit payloads are rejected. It binds repository, running source version and whole-image digest, a newer target version, inactive slot, complete target digest and exact length, rollback floor, expiry, signer identity and detached-signature digest.

`manifest_signing_bytes(payload)` specifies the signing format precisely. Prefix the ASCII bytes `trillionnium.desktop.update-manifest-signature.v1` followed by one NUL byte to the canonical object containing **all manifest fields except `signature_sha256`**. Canonical encoding is `json.dumps(value, ensure_ascii=True, sort_keys=True, separators=(",", ":"), allow_nan=False).encode("ascii")`, with no trailing newline. The only excluded field is envelope metadata needed to avoid a circular signature hash. The actual detached signature must have exactly its declared SHA-256, and OpenSSL must verify that signature over this domain-separated preimage. An unsigned legacy manifest has no admission path. Equivalent JSON whitespace or member order does not change the signed preimage.

`UpdateTrustRoot(signer_id, public_key_pem, expected_public_key_sha256, minimum_version, valid_from_unix, valid_until_unix, revoked=False)` accepts externally approved configuration only. The PEM bytes must match the independently pinned digest; the manifest cannot supply or replace a key. Unknown, revoked, not-yet-valid and expired roots are refused. At most 32 roots, 64 KiB of PEM per root and 64 KiB of detached signature are accepted. `ExternalUpdateSignatureVerifier(roots)` performs real offline verification and returns an admission bound to signer, key digest, actual signature digest, preimage digest, policy digest and verification time. This code consumes approval; it cannot create approval or prove key custody.

`UpdateCoordinator(*, active_slot, current_version, current_image_sha256, max_boot_failures=2, signature_verifier=None, protected_rollback_floor=None, clock=None, recovery_operator_uids=frozenset(), journal_authority=None)` defaults to no signature admission and no authorized operator. A missing explicit floor defaults conservatively to the running version. `clock` defaults to system Unix time; an installed deployment needs a trustworthy time source. `verify_manifest(payload, *, now_unix, signature=None)` requires a matching caller time within five seconds but uses the actual configured clock for decisions, verifies the signature and only then issues a transaction ticket. The source version must match the running version, the target must be newer, and the signed floor must satisfy both the external protected floor and signer minimum without preventing rollback to the source. Expiry is bounded to 31 days.

Signature policy, root validity, expiry, protected floor and non-regressing time are rechecked before staging, immediately before publication and before `arm_first_boot(ticket, *, now_unix)` and again before commit. Commit only advances the in-memory floor monotonically. Persistence and anti-rollback protection of that floor across reboot or whole-directory restoration require independent protected storage and remain an installation prerequisite.

## Durable A/B state

The policy state machine is:

```text
idle -> verified -> staged -> boot_pending -> health_pending -> committed
                                  |                 |
                                  +---- failure ----+-> rollback_pending -> idle
                                                     -> recovery_required
```

`stage_image(ticket, image: bytes, *, now_unix)` is an in-memory whole-image check for source tests. Actual host byte publication uses `stage_image_file(ticket, image_path: Path, slot_store: ImageSlotStore, *, now_unix, fault=None) -> ImageStageReceipt`. `ImageSlotStore(root: Path, *, active_slot)` uses the same private-directory and exclusive-lease rules as `AtomicStateStore`; callers must acquire it or use a context manager. It accepts regular files `slot-A.img` and `slot-B.img` only. The active slot must already contain the complete admitted source image. The state-write API refuses both slot names.

The candidate image is opened through a full absolute no-follow directory walk and must be a nonempty regular file with one hard link, at most 16 GiB. Complete SHA-256 and exact length are verified before creating a staging temporary file. Copying uses at most 1 MiB per read, checks source identity/length/timestamps and the copied full digest, then syncs the private retained temporary descriptor. Immediately before replacement, the store rechecks admission, active image, inactive pathname identity, temporary inode/custody and complete staged bytes. Publication retains that descriptor through atomic replacement and directory sync and checks the resulting named inode and complete digest. Source image validation is not an installed boot observation.

Pre-publication faults leave the active and previously inactive image bytes intact; cleanup removes only the still-owned temporary inode. A substituted foreign temporary file is preserved as evidence. Immediately before attempting atomic replacement the coordinator records publication intent and enters recovery. Any error from the replace call, including an interruption after the kernel changed the pathname but before the call returns, is `ImagePublicationIndeterminate` and puts the coordinator in `recovery_required` with the actual pending publication ticket; the inactive destination may already contain the exact target. `reconcile_image_publication(ticket, slot_store, *, now_unix)` verifies the complete existing active and target files, syncs the target and directory, revalidates pathname/lease identities and current admission, then returns to `staged`. It accepts only this coordinator's recorded indeterminate image publication, so it cannot clear an unrelated boot fault. It never rewrites bytes or repeats a dispatch. Failed sync or binding remains indeterminate.

The booted slot and digest must equal the staged target. Commit requires the actual coordinator-issued health permit after at least 60 stable seconds; boot failure, a repeated boot, dispatch or operator rollback invalidates a previous health permit. Commit rechecks current signature/trust/floor/expiry admission. These caller facts need a trusted installed boot/health adapter and accepted durable receipts; policy methods do not execute a boot or observe health themselves. `AtomicStateStore.write(name, value, *, fault=None)` separately publishes bounded JSON state through exclusive temporary creation, complete write, file sync, atomic replacement and directory sync. Any failure once atomic replacement has been attempted, including `KeyboardInterrupt` or `SystemExit` before the call returns, is `PublicationIndeterminate`; the original cause is retained and durable state must be read and reconciled before retry. Image publication and its reconciliation also classify these process interruptions as indeterminate.

## Failure and replay semantics

Missing slots, substituted bytes, malformed state, changed active image, exhausted sequence, stale ticket, wrong phase, unrelated health receipt and unrelated journal facts fail closed. Two failed first boots open rollback. Rollback must identify the exact admitted source image or the coordinator enters recovery.

`mark_possible_dispatch(ticket) -> DispatchBinding` issues a fresh random 256-bit operation identity bound to manifest digest, sequence, originating phase, target slot and target image, then latches durable reconciliation. There is no automatic replay. The trusted installed dispatch adapter must durably persist this binding/latch before performing effects; this source coordinator does not claim restart reconstruction or an installed journal integration.

Journal reconciliation defaults to disabled. `DurableUpdateJournal(root: Path)` must be explicitly supplied by trusted configuration and hold its private exclusive lease. `verify_journal_reconciliation(ticket)` takes no caller digest or status. It opens `dispatch-<operation_id>.json` through the retained no-follow root, reads a complete private `0600`, one-link regular record of at most 64 KiB and checks the exact closed fields: `schema`, `manifest_sha256`, `sequence`, `operation_id`, `operation`, `target_slot`, `image_sha256`, `status`. The schema is `trillionnium.desktop.update-dispatch-journal.v1`; all operation fields must exactly match the pending dispatch, and status must be terminal or indeterminate. It verifies inode/custody/length/timestamps, syncs file and directory, revalidates identities, and binds the actual raw record digest and root/file identity to a retained coordinator fact. Missing, malformed, substituted or unsynced records cannot clear the latch.

`reconcile_possible_dispatch(fact)` accepts only the actual fact issued by that coordinator and repeats complete record verification and both syncs before clearing. Copied facts, facts from a second coordinator and changed record inodes fail closed. Clearing moves only to `rollback_pending`. The journal root is authority supplied by the trusted installed adapter; a malicious privileged writer of that root can still forge local history. A private record does not itself prove an effect happened, receipt-chain authenticity or whole-directory rollback resistance. Those installed authority and monotonic-anchor integrations remain prerequisites.

`request_operator_rollback(ticket, source_image_path) -> RecoveryDecision` reads the actual local effective UID and requires membership in the externally configured approved operator set. It fully verifies a no-follow regular source image and the protected source version, then authorizes `rollback_only_no_replay`. No supplied UID assertion is accepted. The API neither changes a bootloader nor writes block devices, deletes history, repairs authority directories, clears a possible-dispatch latch or emits a new update. An unresolved dispatch must first be reconciled through the journal adapter. A revoked or expired target cannot prevent an approved operator from diagnosing and authorizing recovery to the exact protected source; target staging and activation still require fresh admission.

## Installed-image qualification

Closing S11 requires an immutable installed-image packet derived from an accepted current G4/S10 lineage, external approved signer roots and monotonic floor/time facilities, durable journal wiring and a real boot/health/recovery adapter. Current regular-file publication and test-only keys supply source/host evidence, not installed authority. The installed QEMU gate must exercise normal signed update, unsigned or wrong-key rejection, downgrade, expiry, wrong source, image/slot substitution, first-boot/health failure, rollback and restart reconciliation.

Every durable cutpoint must be exercised before and after temporary creation, complete write, file sync, atomic replacement and directory sync, plus interrupted health and rollback. Host exception injection is useful source evidence but is not raw power loss evidence. The local corpus creates disposable test keys solely for real positive/negative OpenSSL verification and fails if that verifier is absent. It includes attempted wrong-signer key substitution at the actual verifier boundary, sealed descriptor mutation, inherited fork commit after parent boot failure, inherited store/journal/staging refusal, child-close lease retention and foreign-thread refusal. These host tests produce no production qualification.

The installed packet must bind source commit/tree, source/target image digests, signed manifest and detached-signature digests, approved root/policy/floor identity, booted slot, journal/receipt identities, QEMU command, firmware/kernel/package locks and terminal results. Source movement or image rebuild invalidates it.

## Evidence invalidation

S11 source evidence invalidates on contract, implementation, corpus, workflow, base image, image manifests, receipt/journal, package or toolchain changes. Installed evidence additionally invalidates on any source/target digest, QEMU substrate, firmware, kernel, signer trust/revocation policy, protected floor, clock facility, systemd unit or durable-state change.

Exact-head and live prospective-merge jobs must succeed on the final immutable object. Exact-head push checks cover `main` and `codex/**`; pull requests check the live merge object and its ordered parents. Historical S10/D1/D2I artifacts and predecessor update experiments remain provenance and do not transfer.

## Non-claims

This source candidate does not claim an installed QEMU update, survival of raw power loss, physical hardware qualification, verification of an actual production signature, production key custody, independent floor persistence or a published release. Those facts require corresponding external facilities and independent acceptance. No source check promotes qualification or default production activation.
