# 开发路线与首轮任务

版本：0.1。基线日期：2026-10-16。当前只完成文档初始化，以下实现任务尚未执行。

## 1. 工作原则

单一主线、真实应用驱动、每个阶段有可执行结果。优先复用合适上游，不同时重写所有已有组件。普通开发不设重复审批、多重签名或空壳“资格门禁”；同一条测试与结果记录服务研发与验证。

按任务依赖推进，不凭假定工期承诺完成日期。复杂阶段允许明确缩小测试 profile，不允许伪造完成或悄悄删除长期 Linux/Android 兼容目标。

## 2. 里程碑

| 阶段 | 具体交付 | 最低验收 | 后续依赖 |
| --- | --- | --- | --- |
| M0 基础固定 | 上游 commit/工具链/rootfs 固定、Linux 对照样本、最小构建入口 | 干净环境复现候选内核启动，记录准确来源和基线 | M1 |
| M1 内核基础 | 派生或新实现的内核、地址空间、线程、基础存储网络 | QEMU 进程隔离、基础 ELF、故障与资源回收 | M2 |
| M2 Hepta 运行与原生接口 | 真实 Hepta 依赖闭包、control ABI、资源域与执行桥 | 同一新内核上的真实 Hepta -> CPU 预算生效 -> kill 后仍可恢复 | M3、M4 |
| M3 Linux 扩展 | 线程/IPC/持久化/真实应用矩阵、差分回归 | 固定应用场景与重启/并发结果，可列出明确缺失接口 | M5 |
| M4 Android 原型 | 锁定 AOSP、Binder、系统服务、图形输入、首个 APK | 原 APK 真实场景、native 库分类、适用测试与故障记录 | M6 |
| M5 裸机与本地 AI | 单一实机、实际驱动与本地模型路径 | 裸机启动、设备实际计算、数值正确与恢复 | M6 |
| M6 产品整合 | Rust 桌面、多应用、Android 扩展、更新恢复 | 指定设备/应用清单的完整使用与持续稳定性 | 逐项扩大支持 |

M4 可在必要基础接口具备后与 M3 并行；不要求先实现所有 Linux 功能才开始 Binder。M5 的 CPU 实机工作可先于完整 GPU，GPU 和移动设备单独推进。

## 3. 下一轮立即可做的 M0 任务

### M0.1 锁定代码与许可来源

选用 Asterinas v0.19.0 作为候选参照，解析精确 commit、工具链和构建依赖；核对许可及需要保留的声明。决定复用整个内核还是以 OSTD 为底座，记录一个明确选择，而不是同时开两套长期平行实现。

交付：上游锁定文件、来源说明、可重现的构建命令与最小差异说明。此时不删除上游署名、不重写 README、不迁入旧桌面代码。

### M0.2 建立不依赖 Hepta 的内核启动

使用固定 QEMU CPU/内存/设备与测试 rootfs 构建运行，捕获串口与退出状态。先确认基础 ELF、定时器和最小存储/网络路径，失败时修具体复现，不添加与启动无关的平台。

交付：一次完整日志、构建产物哈希和可重跑命令。QEMU 成功记为虚拟硬件测试，不写为物理机支持。

### M0.3 固定 Linux 与 Hepta 对照

从固定上游快照构建真实 Hepta 组件，记录二进制和依赖闭包，在原 Linux 下执行最小场景。盘点 syscall、文件、线程、Unix IPC 与持久化需求，输出第一张有证据的缺口表。

交付：固定 ELF/rootfs 清单、真实 trace 与最优先的缺失接口。不得将 HTTP mock 或仅 --help 输出记为完整 Hepta 可运行。

### M0.4 实现最小 ABI 编解码

按 NATIVE_ABI.md 的固定请求头实现 no_std 库与测试；确定实际 opcode、错误映射、请求边界及兼容设备入口。只实现 QueryAbi、ReadUsage、InstallBudget 所需最小集合。

交付：编解码、截断、溢出、未知字段和能力句柄负向测试。共享同一协议代码，不为内核和客户端建立互不一致的两个 schema。

## 4. M2 的首个端到端实验

同一新内核中启动真实 Hepta、两个有资源竞争的工作负载与独立观测器。先记录固定策略基线，再由现有 Hepta 主链安装目标任务预算。观测器确认正确目标、实际 CPU 时间、策略 revision 与其他任务不受越权影响。

接着停止模型服务与 Hepta，验证独立任务和内核继续工作、管理委托按契约失效且本地恢复可用。最后重启并证明旧句柄/旧请求不能作用于新对象。详细步骤见 VALIDATION.md。

## 5. 并发开发的边界

可以并行：ABI 与测试、Linux 语义修复、AOSP 依赖盘点、上游设备调查。共享的关键边界（内核对象、任务身份、资源计费、ABI）保持单一实现与测试。

同一改动对应一个清楚的提交，相关构建和测试随提交进行；不为制造并发数拆出互相依赖的空 PR，不引入与本阶段无关的 CI 矩阵。仓库重建后本轮不启用继承来的自动工作流。

## 6. 重新评估条件

如果已选上游无法满足核心接口，先用最小原型量化修改成本，再调整派生边界。GPU/Android 阻塞不应导致复制第二套 Hepta。若某项需要 VM，标记为 VM 并说明原生替代路径与成本。

如果 Hepta 策略没有超越固定策略，保留固定策略作为默认，继续改进观测与策略；不能为了“AI-native”强制让所有调度都经过推理。
